# ZCU111 CVA6 Bring-Up Design

Date: 2026-05-11

## Goal

Port the CVA6 APU FPGA flow to the AMD/Xilinx ZCU111 board in a staged way. The first milestone is a bare-metal bring-up with the smallest useful hardware surface. After that, the design must grow toward PL DDR4 integration, and then Linux execution on the CVA6 core.

The repo should remain the source of truth. The ZCU111 target should be generated by the existing Make/Vivado flow rather than maintained as a hand-created Vivado project.

## Scope

### Phase 1: Bare-Metal Without DDR4

Build a minimal ZCU111 FPGA target that can synthesize, program, and run simple bare-metal code on CVA6.

Included:

- CVA6/APU in programmable logic.
- New `BOARD=zcu111` path in the existing FPGA build flow.
- New board define/header, tentatively `corev_apu/fpga/src/zcu111.svh`.
- New board constraints, tentatively `corev_apu/fpga/constraints/zcu111.xdc`.
- JTAG debug path for OpenOCD/GDB.
- UART output.
- LEDs through GPIO or simple board-level wiring for visibility.
- Local AXI memory mapped at the existing DRAM base, `0x8000_0000`.

The local memory may be implemented with BRAM or URAM. It only needs to be large enough for hello-world and small bare-metal tests. A starting target of 256 KiB to 1 MiB is acceptable.

Excluded from phase 1:

- PL DDR4.
- PS DDR4 access.
- SD boot.
- Ethernet.
- Linux or Zephyr boot.
- RFDC and RFSoC-specific datapath blocks.

### Phase 2: PL DDR4

Replace the temporary local AXI memory with the ZCU111 PL-side DDR4 memory.

Included:

- DDR4 controller IP suitable for the ZCU111 PL DDR4 interface.
- Board-specific DDR4 constraints and IP configuration.
- Clock/reset/calibration wiring.
- AXI connection from the existing APU DRAM master path to the DDR4 controller.
- Bare-metal validation using the same GDB/OpenOCD flow as phase 1.

The existing 7-series `mig_7series` path should not be reused for ZCU111 DDR4. The design should follow the existing UltraScale+/DDR4 direction already partially represented by the VCU118 conditionals in `ariane_xilinx.sv`, adjusted for ZCU111.

### Phase 3: Linux On CVA6

After PL DDR4 is stable, the next objective is to boot Linux on the CVA6 core.

Included:

- Boot path using the CVA6 boot ROM and a board-appropriate second-stage payload.
- Device tree aligned with the ZCU111 CVA6 memory map and enabled peripherals.
- UART console.
- DDR-backed kernel and root filesystem loading path.
- Decide whether Linux is loaded through SD, JTAG, or another loader once DDR4 is proven.

Linux is intentionally not part of phase 1. It depends on stable DDR4, a correct device tree, and enough peripheral support to debug failures.

## Architecture

The port should reuse the current CVA6 repository layering:

- `core/`: CVA6 CPU RTL.
- `corev_apu/src/ariane.sv`: wrapper around CVA6.
- `corev_apu/fpga/src/ariane_xilinx.sv`: FPGA top-level integration.
- `corev_apu/fpga/src/ariane_peripherals_xilinx.sv`: UART, PLIC, timer, GPIO, SPI, Ethernet integration.
- `corev_apu/tb/ariane_soc_pkg.sv`: SoC memory map.
- top-level `Makefile` and `corev_apu/fpga/Makefile`: build orchestration.

Phase 1 should make the smallest ZCU111-specific changes needed to elaborate a new board target:

- Add `zcu111` to the top-level board selection.
- Add ZCU111 board constraints and global defines.
- Add the ZCU111 branch to the FPGA TCL flow.
- Provide a local AXI memory implementation on the DRAM slot.
- Keep peripheral selection conservative: UART, JTAG, and LEDs only.

## Data Flow

In phase 1, CVA6 and the debug module remain AXI masters into the existing AXI crossbar. The crossbar still maps DRAM to `0x8000_0000`, but that target is backed by local BRAM/URAM instead of external DDR.

In phase 2, the same DRAM target is backed by the ZCU111 PL DDR4 controller. Keeping the address map stable lets the same bare-metal software and debugger scripts validate both phases.

In phase 3, Linux should use the same DRAM base and UART console. The device tree and boot payload must describe only the peripherals that are actually stable on the ZCU111 design.

## Validation

Phase 1 is successful when:

- Vivado can elaborate and synthesize the ZCU111 target.
- A bitstream can be generated and programmed.
- OpenOCD detects one RISC-V hart.
- GDB can load an ELF at `0x8000_0000`.
- A bare-metal program prints through UART or visibly toggles LEDs.

Phase 2 is successful when:

- DDR4 calibration completes.
- The same bare-metal ELF runs from DDR4.
- A memory test can write/read a meaningful DDR4 range through CVA6.

Phase 3 is successful when:

- Linux reaches the UART console on CVA6.
- The kernel uses the ZCU111 PL DDR4 memory region.
- The boot path is reproducible from repo scripts and documented commands.

## Error Handling And Debug Strategy

Bring-up should isolate failures by phase.

For phase 1:

- If JTAG fails, debug pin constraints, reset polarity, and debug module clocks before touching memory.
- If UART fails but GDB works, validate UART pins, baud rate, and boot/software configuration.
- If memory fails, use small linker scripts and direct GDB memory writes before running larger software.

For phase 2:

- Treat DDR4 calibration as the first gate.
- Keep the phase 1 local memory path available as a fallback until DDR4 is proven.
- Validate the DDR4 controller independently with simple AXI traffic before attempting Linux.

For phase 3:

- Keep Linux boot changes separate from DDR4 integration changes.
- Start with a minimal device tree and add peripherals only after the UART console is reliable.

## Open Questions

- Exact ZCU111 pins for UART, JTAG, LEDs, reset, and clocks must be taken from the ZCU111 constraints/reference files.
- The local memory size for phase 1 should be chosen after checking ZCU111 BRAM/URAM utilization and CVA6 resource usage.
- The final Linux boot medium is not fixed yet. SD boot is likely, but JTAG-loaded payload is acceptable for initial Linux debugging after DDR4 works.
